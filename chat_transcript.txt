--------------------------------------------------------------------------------
A1. PROBLEM INTAKE
--------------------------------------------------------------------------------
User shared the "Buy or Wait" hackathon problem statement: build a system that
decides whether a user can afford a requested expense, using
dataset/requests.csv as the only file requiring predictions, with supporting
context in financial_profiles.csv, financial_events.csv, exchange_rates.csv,
request_payment_options.csv, messages.csv, images.csv, and a sample_requests.csv
answer key. Required outputs per request: amount_safe_to_pay,
affordability_status, recommended_payment_method, payment_plan,
earliest_date_for_full_payment, spending_changes_needed, decision_explanation.

Assistant proposed an architecture up front: a deterministic 90-day balance
forecast + rule-based decision engine, with AI reserved for interpreting
unstructured inputs (receipt images, free-text messages) rather than doing the
arithmetic itself -- to keep the safety-critical numbers reproducible and
auditable.

--------------------------------------------------------------------------------
A2. INITIAL SCAFFOLD (built before any real data was available)
--------------------------------------------------------------------------------
Built a placeholder project structure and packaged it as code.zip on request:
- src/data_loader.py -- generic CSV loading + join indices
- src/currency.py -- FX conversion, schema guessed pending real data
- src/event_resolution.py -- stub for blank-amount-from-image / message
  amendment logic
- src/forecast.py -- 90-day safety check: run_forecast, max_safe_payment_today
  (binary search), earliest_safe_full_payment_date (day-by-day scan)
- src/decision_engine.py -- stub for eligibility rules + tie-break ranking
- src/pipeline.py -- end-to-end runner with per-request error isolation
- tests/test_forecast.py -- 8 synthetic unit tests against the forecast math,
  independent of real data (all passing)
- README.md documenting what was solid vs. stubbed pending real schema

A3. REAL DATASET UPLOADED -- SCHEMA DISCOVERY
--------------------------------------------------------------------------------
User uploaded the real 9 CSVs plus 16 receipt/invoice/payslip images (as
generic WhatsApp-export image files, not yet matched to their image_id).

Assistant's investigation, iteratively, via direct pandas inspection of the
real files:
- Confirmed exchange_rates.csv schema (rate_date/from_currency/to_currency/rate)
  matched the original guess exactly.
- Discovered financial_events.csv has NO explicit "is_recurring" flag or
  frequency column -- recurrence has to be inferred from history by grouping
  each user's events by category and checking interval consistency.
- Mapped out status semantics: cancelled/failed always excluded; unrealized
  (non-cash investment marks) always excluded; pending CREDITS excluded
  (unconfirmed income) but pending DEBITS included (known future obligations --
  the financially safer reading); scheduled and settled included as-is.
- Confirmed requests.csv (250 real requests) and sample_requests.csv (25 worked
  examples with known-correct answers, disjoint user set) both draw from the
  same 275-user financial_profiles.csv -- sample_requests.csv established as
  the calibration/validation set for the rest of the build.
- Visually identified and matched all 16 uploaded images to their correct
  image_id (cross-referencing amount/date/currency against
  financial_events.csv's blank-amount rows) and saved them as proper PNGs at
  dataset/media/images/image_01.png .. image_16.png.
- Read all 215 messages in messages.csv and catalogued ~14 distinct template
  families (salary changes, unconfirmed bonus/commission/gig payouts, rent
  increases, internal transfers, an advance-fee scam pattern, etc.), in English
  and Bahasa Indonesia.
- Confirmed real cross-currency events exist (e.g. USD salaries for IDR/INR
  users) dated to align with available exchange_rates.csv rows.

A4. FIRST BUILD PASS -- RULE-BASED (pre-AI-requirement) VERSION
--------------------------------------------------------------------------------
Built out full implementations against the real schema:

  events' amounts, populated by the assistant visually reading each of the 16

- src/forecast.py (rebuilt) -- build_user_timeline() composing recurring-series
  projection, message-fact application, and currency conversion into a single
  cashflow timeline; run_forecast() / max_safe_payment_today() /
  earliest_safe_full_payment_date() implementing the 90-day safety check.
- src/decision_engine.py (rebuilt) -- eligibility rules for
  full_payment/partial_payment/installments/wait/not_recommended, spending-change
  candidate generation (stop:/reduce_to:, confirmed against real examples that
  reduce_to always clamps to the event's own minimum_allowed_amount), and the
  spec's 6-level tie-break ranking.

--------------------------------------------------------------------------------
A5. DEBUGGING AGAINST THE 25-SAMPLE VALIDATION SET
--------------------------------------------------------------------------------
Iteratively ran the pipeline against sample_requests.csv and fixed two real
bugs found this way:
- A one-off bulk purchase (a large nuts-and-spices receipt) was being picked up
  as the "most recent occurrence" of a weekly grocery series and projected
  forward as if it recurred every week -- fixed by using the median of the last
  3 occurrences as the representative recurring amount (balances outlier
  resistance against responsiveness to genuine level shifts, e.g. an already-
  reflected salary cut).
- A gig-payout-pending message wasn't stopping that income series from being
  projected forward with full confidence -- fixed by treating
  "income_unconfirmed" with category_hint "gig_income" as a series-stopping
  fact, not just a single-occurrence exclusion.

Also fixed a real output-format bug: large amounts (tens of millions, common in
IDR) were rendering in scientific notation (1.5656e+07) via Python's default
:g format spec -- replaced with a dedicated _format_amount() helper producing
plain decimals.

Final calibration result from this phase: 15/25 sample requests matched exactly
on both affordability_status and recommended_payment_method; 18/25 matched on
method alone. Investigated but did not fully resolve a consistent one-directional
gap in amount_safe_to_pay on the remaining cases (this model finding somewhat
more safe-to-spend margin than the reference answers), including a partially-
confirmed hypothesis about whether not-yet-received future income should count
toward today's safe-to-pay amount -- documented as a known, disclosed limitation
rather than papered over.

Ran the full 250-request set: zero errors, all output-format invariants clean
(0 <= amount_safe_to_pay <= requested_amount, affordable_now date consistency,
valid payment_plan/spending_changes_needed formatting). Packaged as code.zip
+ output.csv with an initial evaluation/usage_report.md documenting a
zero-API-call, fully deterministic design.

A6. CRITICAL REQUIREMENT CORRECTION -- "MUST BE AI-BASED"
--------------------------------------------------------------------------------
User flagged that the hackathon explicitly requires an AI-powered system, not a
zero-API-call deterministic one. Assistant confirmed this was a real gap (no
model calls existed anywhere in the built pipeline) and converted the two
components that were standing in for AI work to real Anthropic API calls:
- src/ai_client.py (new) -- shared Anthropic client wrapper + UsageTracker,
  recording real token usage for later cost reporting.
- src/image_extraction.py (v2) -- replaced the hardcoded lookup table with a
  real vision API call per receipt image, strict-JSON response format, disk
  cache keyed by image path.
- src/message_facts.py (v2) -- replaced the regex classifier with a real LLM
  call per message using a constrained JSON schema identical in shape to the
  original MessageFact dataclass (so downstream forecast/decision code needed
  no changes), disk cache keyed on message id + content hash.
- src/pipeline.py -- added an up-front ANTHROPIC_API_KEY check that fails fast
  and clearly, after finding and fixing a real bug where a missing key was
  being silently swallowed by the per-call exception handler and cached as a

  RuntimeError (missing key) while still catching genuine per-call API/parsing
  failures.
- Added write_usage_report() generating evaluation/usage_report.md from real
  recorded token counts after each run, rather than a hand-written report.

No live Anthropic API key was available in this session's sandbox, so this
phase produced fully-reviewed, syntax-checked, unit-tested code (9/9 forecast
tests passing, unaffected since they construct synthetic timelines directly)
but could not execute a live end-to-end run itself. User was given exact
run instructions and warned explicitly that accuracy against sample_requests.csv
had not been re-validated post-conversion since doing so required real API
spend.

--------------------------------------------------------------------------------
B5. VISION MODEL SELECTION -- TWO FALSE STARTS, ONE WORKING FIX
--------------------------------------------------------------------------------
User asked for the lowest-disk-space vision model. Actual sequence:

  a) moondream (~829MB, smallest in Ollama's library) -- pulled successfully,
     but turned out to be a confirmed, longstanding upstream bug: it returns an
     EMPTY response for every image-containing prompt on this Ollama version
     (verified via OpenAI-compatible endpoint AND Ollama's native /api/chat and
     /api/generate; matched known GitHub issues, e.g. ollama/ollama#4063,
     #6365; vikhyat/moondream#151). Removed.

  b) llava-phi3 (~2.9GB) -- pulled, and this one actually produces text output
     for images, but exposed real robustness gaps: markdown-fenced JSON
     (```json ... ```), invalid JSON with unquoted thousands-separator commas
     (e.g. "amount": 431,896,027.35), and currency-symbol/comma strings
     (e.g. "$1,065,872"). Also showed severe run-to-run non-determinism at the
     default sampling temperature (same image: $431M, then $145, then $45 across
     repeated calls).

  Fixes applied in src/ai_client.py:
  - strip_json_fences(): strips ```/```json wrappers before json.loads.
  - sanitize_unquoted_amount_commas(): repairs the invalid-JSON comma case.
  - coerce_amount(): tolerantly converts a currency-symbol/comma string or
    number into a float, or None if unrecoverable.
  - call_ollama() now defaults to temperature=0, which substantially (not
    perfectly) reduced the non-determinism.
  - Verified end-to-end: all 16 real receipt images resolved to numeric amounts
    (previously all None). Re-ran the 25-sample and full 250-request pipelines
    successfully.

       - message_facts.py: same treatment, degrading to a no_op fact instead of
         erroring the whole request.

B7. FINAL VERIFICATION RUN -- REAL BUG FOUND AND FIXED
--------------------------------------------------------------------------------
During the final full-dataset regeneration (to make sure output.csv on disk
matches the very latest code), a real, serious issue surfaced:

- 117 out of 250 rows in output.csv came back as
  "ERROR during processing: Could not reach local Ollama ... model 'llama3.1:8b'
  ... HTTP Error 404: Not Found."
- Root cause: a batch of Groq calls failed (consistent with rate-limiting under
  the call volume of a cold full run), triggering the text fallback path -- but
  llama3.1:8b (the fallback model) had never actually been pulled, only
  llava-phi3 (the vision model) had. The old message_facts.py code treated any
  RuntimeError from the fallback as a fatal config error and let it propagate,
  which the per-request handler in pipeline.py then recorded as a hard error
  row instead of a graceful "no_op" fact.
- Confirmed the existing on-disk caches were NOT corrupted by this: the old
  code raised before writing to cache, so no bad data was ever cached -- only
  requests that hit this path were left unprocessed/errored, not silently
  wrong.

Fix applied: message_facts.py now catches OllamaUnavailableError specifically
(mirroring the image path) and degrades that single message to a no_op fact
with a warning, instead of erroring the whole request. A regression test was
added (test_message_facts_ollama_unavailable_degrades_to_no_op_not_an_error_row)
that reproduces this exact scenario. Full test suite: 22/22 passing.

A background `ollama pull llama3.1:8b` was also started to make the fallback
model actually available locally, but the user interrupted and explicitly
cancelled it mid-session ("stop cancel llama pull" / "cancel the installation of
ollama llama 3.2"). Current confirmed state: only llava-phi3 is installed;
llama3.1:8b is NOT installed. This is fine given the code fix above -- Ollama
being unavailable for the text fallback now degrades gracefully instead of
producing error rows, so the pipeline is safe to run either way, though message
extraction accuracy for any Groq-failed message will fall back to a no_op
(unresolved) fact rather than a real classification until/unless llama3.1:8b is
pulled.
